# Airified llama.cpp deployment contracts

- The public repository is `airium/llama-cpp-airified`. Keep project branding and the default sibling `llama-cpp-kv-caches/` directory model/hardware-independent; preserve model-specific profile names, API aliases and explicit host path overrides.
- Use Conventional Commits for every commit (`type(scope): summary`, with an optional scope). Add an explanatory body when useful. Preserve the configured signing policy, and do not commit or push without explicit user authorization.
- The engine is the pinned vendor base plus the local patches listed in `upstream.json`. `build.sh` applies them without resetting unrelated edits. Keep the patch manifest, default build directory, draft quantizer, profiles and deployment README aligned.
- Future implementation, experiments, and qualification are **tensor-parallel only**. Preserve non-TP profiles and archived results as historical evidence, not candidate deployments. Target-only diagnostic controls must also use TP.
- For this chat session, use **three DFlash2 proposals** (`DRAFT_TOKENS=3`) by default until the user changes the convention. Other lengths are explicit diagnostic/reference controls. This selected working baseline does not retroactively qualify a failed exact-context-end check; preserve that distinction in reports.
- The selected deployment image policy is **64 minimum / 4096 maximum visual tokens per image**, with GPU vision. Preserve explicit host overrides. A minimum-token setting is a preprocessing floor, not a fixed image size; do not describe historical full-context qualification at a different image minimum as a new qualification run.
- Follow the workspace's prospective speed-benchmark matrix: **32K/1024 and 128K/1024, natural prose and code, prefill and decode tokens/s** (eight headline values per route). Do not carry the archived 4K or synthetic 32K/512 suites into routine future speed trials; keep their historical evidence unchanged. This memo alone does not call for a new benchmark run.
- Investigate and implement structural/kernel/runtime changes first. Retain the user-selected working **1024/64 target/draft microbatches, logical batch 2048 and three proposals** for new implementation comparisons; defer broader microbatch, proposal-length and draft-precision/configuration searches until that work is complete. Preserve archived 1024/128 and 512/128 controls at their original settings. Do not restart parameter sweeps merely to refresh benchmarks.
- The ongoing framework investigation permits temporary diagnostic context reduction (for example 133120 configured tokens to benchmark 131072 input + 1024 output). Label these trials; do not promote them as 262144 qualification. The qualified default uses the original Q8 draft and shared target head; retain the original Q4 shared-head fallback. Changed candidates still need final full-context/vision qualification.
- Preserve approximately eight-bit target weights and target KV, 262144 total context tokens, vision, and DFlash2. Prefer an approximately eight-bit drafter; on memory pressure, lower drafter precision before moving unchanged vision weights and computation to CPU. Do not silently lower target/KV precision, context, or image detail, or substitute MTP.
- Keep the launcher, example configuration, build/preparation defaults, and deployment-first README aligned. Preserve explicit host overrides and model files. Shared-head routes use the original downloaded drafts; legacy private-head drafts are generated outside source Git. Do not rewrite target checkpoints.
- Read the workspace instructions and inspect live processes, GPUs, and ports before inference. Use isolated trials and restore any authorized interrupted service. Read vendor instructions before changing upstream source.
- Keep investigation narratives and benchmark results in the existing runtime archive's `main.md`, with raw evidence alongside it. Do not recreate a separate performance note. Distinguish measured results, source-derived estimates, and unverified hypotheses.
- Keep the public README focused on the current deployment and its measured performance. Superseded parameter rows and detailed measurement chronology belong in the archive, not repeated user-facing caveats; refresh measurements when needed.
- Health-ready and configured context do not establish capacity. Changed deployment candidates require actual image and full-context qualification; retain failed exact-token checks as failures. Do not infer CUDA graph replay or KV persistence from configuration alone.

- Automatic persistent prefix reuse is part of the selected deployment. Keep active attention GPU-resident; storage I/O is for safe snapshot/restore boundaries, not per-token SSD attention paging. Preserve target/draft state, recurrent checkpoints and media identity together; attention-only cache hits are insufficient for this hybrid model.
- Persistent payloads live outside source Git at the launcher's configured `KV_CACHE_DIR`, with one engine-process writer per root. Keep byte quotas, bounded host buffers, atomic commits, identity checks and corruption recovery intact. Qualify persistence with actual fresh-process reuse counts/output/draft behavior, not file creation or warm-process timing alone.
